# 首版采用 PyTRIO 单一托管训练后端

尽管用户已有可独占的 4×A100 40GB，首版仍选择 PyTRIO 上的 LoRA 训练，把四天目标、一周上限内的精力集中于交互轨迹、训练信号和评测，并减少此前项目因多套训练基础设施而失去可维护性的风险。相较本地训练、Tinker 或另租两张 80GB 卡，这一选择接受了平台模型清单、计费和检查点语义的约束，新增 API 实验支出总上限为 ¥200。首版只维护这一生产训练后端；未来替换后端需要重新验证采样、教师评分、权重衔接与结果可比性，接口的测试替身不算第二个生产后端。

2026-09-29 更新：实际可用的本地资源为一张 A100 40GB（见 AGENTS.md），只用于开发调试推理，不改变本决定。

## 2026-10-03 修订：允许经验证的本地采样与评测

用户在任务 21 调整了本地推理的范围：同一张 A100 可运行原始 Qwen/Qwen3.5-4B 与 PyTRIO 已有 SFT sampler 导出的权重，用于示范采样和评测。PyTRIO 仍是唯一生产训练后端；本地不新增优化器、训练框架或第二套 Harness。

本地实验记录必须绑定基模 revision、权重与 tokenizer／模板哈希、导出 checkpoint 身份和推理条件，并通过实际服务身份与 token／逐 token logprob 探针。结构或编码不兼容、权重未加载或响应回退到另一模型时显式失败。完整训练状态与推理权重仍分开记录。任务 20 的其他模型、旧服务和旧运行继续作为开发证据，不能通过更改标签追认为基线。

实现选择先合并已有 LoRA 再用 vLLM 推理：直接加载在目标模型的 tied output head 上被 vLLM 0.17.1 明确拒绝；合并保留输入 embedding，以 FP32 计算增量，再舍入为原始 BF16 权重，输出 head 独立保存。转换步骤、配置变化与派生权重哈希均须记录。云端基模 revision 未公开，本地不能据模型名或 tokenizer commit 宣称两端权重逐位相同。

这一选择减少新增付费训练前的导出与评测风险，但引入本地权重转换和推理条件验证的维护成本。冒烟成功只验证链路；能力改善仍按原有独立评测口径判断。所有新增付费远端请求继续受项目总账和本轮累计 ¥5 子额度约束，可用资金更少时遵守更小的额度。
